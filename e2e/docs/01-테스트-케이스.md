# E2E 테스트 케이스 명세

LabelSea의 **워크스페이스 → 프로젝트 → 작업/검수** 흐름을 사람이 읽고 손으로도 따라 할 수 있게 적은 명세입니다.
각 케이스 번호는 자동화 스크립트의 테스트 이름과 1:1로 대응합니다 (예: `TC-AC-003` → `tests/api/01-access-control.spec.js`).

- 실행 방법: [../README.md](../README.md)
- 알려진 이슈: [02-알려진-이슈.md](02-알려진-이슈.md)

---

## 1. 테스트 계정

비밀번호는 모두 `test1234`. 이메일은 `localtest_{역할}@test.com` 규칙입니다.
(한글은 이메일 주소에 쓸 수 없어 작업자→`annotator`, 검수자→`reviewer`로 표기합니다. 화면에 뜨는 이름은 한글입니다.)

| 표시 이름 | 이메일 | 이 사람의 역할 |
|---|---|---|
| 작업자1 | `localtest_annotator1@test.com` | 워크스페이스 A·B를 넘나드는 멀티 프로젝트 작업자 |
| 작업자2 | `localtest_annotator2@test.com` | 워크스페이스 A의 A1 전담 작업자 |
| 작업자3 | `localtest_annotator3@test.com` | 워크스페이스 B 전담 — **워크스페이스 A에 대해서는 외부인**(접근 거부 테스트 대상) |
| 검수자1 | `localtest_reviewer1@test.com` | 워크스페이스 A의 A1·A2 검수 (멀티 프로젝트 검수자) |
| 검수자2 | `localtest_reviewer2@test.com` | 워크스페이스 B의 B1·B2 검수 |
| PM1~PM4 | `localtest_pm1~4@test.com` | 각각 A1, A2, B1, B2의 프로젝트 매니저 |
| WM1 | `localtest_wm1@test.com` | 워크스페이스 A 매니저 |
| WM2 | `localtest_wm2@test.com` | 워크스페이스 B 매니저 |

## 2. 목 데이터 구성

```
[E2E] 워크스페이스 A  (매니저: WM1)
├── [E2E] A1 감성 분류 (전수 검수)   검수전략 FULL_REVIEW   태스크 40건
│     PM1 / 작업자1·작업자2 / 검수자1
└── [E2E] A2 감성 분류 (표본 검수)   검수전략 RANDOM_SAMPLING(0.5)   태스크 6건
      PM2 / 작업자1 / 검수자1

[E2E] 워크스페이스 B  (매니저: WM2)
├── [E2E] B1 감성 분류 (전수 검수)   검수전략 FULL_REVIEW   태스크 8건
│     PM3 / 작업자1·작업자3 / 검수자2
└── [E2E] B2 감성 분류 (검수 없음)   검수전략 NONE   태스크 6건
      PM4 / 작업자3 / 검수자2
```

라벨 설정은 네 프로젝트 모두 동일한 감성 분류(`긍정` / `부정` / `중립`, 단일 선택)입니다.
태스크는 워크스페이스에 JSON을 업로드 → **작업집합(태스크 풀)** 으로 묶기 → 프로젝트에 연결하는,
제품의 실제 경로를 그대로 거쳐 만들어집니다.

### 배정 매트릭스 (권한 기대값의 기준)

| | A1 | A2 | B1 | B2 | 워크스페이스 A 멤버 | 워크스페이스 B 멤버 |
|---|---|---|---|---|---|---|
| 작업자1 | 작업자 | 작업자 | 작업자 | — | ○ | ○ |
| 작업자2 | 작업자 | — | — | — | ○ | ✕ |
| 작업자3 | — | — | 작업자 | 작업자 | **✕** | ○ |
| 검수자1 | 검수자 | 검수자 | — | — | ○ | ✕ |
| 검수자2 | — | — | 검수자 | 검수자 | ✕ | ○ |
| PM1~4 | PM | PM | PM | PM | ○(PM1·PM2) | ○(PM3·PM4) |
| WM1 | (매니저 권한) | (매니저 권한) | — | — | 매니저 | ✕ |
| WM2 | — | — | (매니저 권한) | (매니저 권한) | ✕ | 매니저 |

## 3. 접근 권한 테스트 (TC-AC)

자동화: `tests/api/01-access-control.spec.js` — API 응답을 직접 확인합니다.
화면은 메뉴를 숨겨 줄 뿐이고 실제 차단은 서버가 하므로, "URL을 직접 치고 들어오는" 경우까지 보려면 API를 봐야 합니다.

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| TC-AC-001 | 작업자/검수자는 배정된 프로젝트만 본다 | 각 계정으로 프로젝트 목록 조회 | 배정 매트릭스와 정확히 일치하는 목록만 반환 |
| TC-AC-002 | 워크스페이스 매니저는 전부 본다 | WM1으로 워크스페이스 A의 프로젝트 목록 조회 | A1·A2 모두 보임 |
| TC-AC-003 | 비멤버는 남의 워크스페이스를 못 연다 | 작업자3으로 워크스페이스 A 상세 조회 | **404** (존재 자체를 숨김) |
| TC-AC-004 | 비멤버는 하위 리소스도 못 본다 | 작업자3으로 워크스페이스 A의 멤버/프로젝트/작업집합/요약 조회 | 모두 **403** |
| TC-AC-005 | 워크스페이스 목록도 소속으로 걸러진다 | 작업자3·WM1으로 각각 워크스페이스 목록 조회 | 각자 **소속된 워크스페이스만** 보임 (아래 주의 참고) |
| TC-AC-006 | 비멤버는 프로젝트를 수정 못 한다 | 작업자3이 A1 제목 변경 시도 | **403** |
| TC-AC-007 | 작업자는 멤버 배정을 못 바꾼다 | 작업자1이 A1에 멤버 추가 시도 | **403** |
| TC-AC-008 | PM은 멤버를 배정/해제한다 | PM1이 A1에 멤버 추가 후 해제 | 추가 201 → 목록에 보임 → 해제 후 사라짐 |
| TC-AC-009 | 남의 프로젝트는 검수도 못 한다 | 검수자2가 A1 검수 대상 조회 | **403** |
| TC-AC-010 | 배정된 검수자는 조회된다 | 검수자1이 A1 검수 대상 조회 | 200 |
| TC-AC-011 | 멀티 워크스페이스 배정이 동작한다 | 작업자1이 A1·A2·B1을 각각 열기 | 모두 200, 역할은 `annotator` |
| TC-AC-012 | 작업집합은 매니저만 만든다 | 작업자3 / WM2가 각각 워크스페이스 B에 작업집합 생성 | 작업자3 **403**, WM2 성공 |
| TC-AC-013 | 워크스페이스 생성 권한 | 작업자1 / WM1이 각각 워크스페이스 생성 | 작업자1 **403**, WM1 성공(생성자가 매니저가 됨) |
| TC-AC-014 | 해제했던 멤버 재배정 | 워크스페이스 멤버 해제 후 프로젝트 멤버로 재배정 | 201, 워크스페이스 멤버십도 되살아남 (500 회귀 방지) |

> **TC-AC-005 주의** — 조직 전체 목록을 보는 것은 **슈퍼 관리자**(조직 소유자 또는 `super_admin` 역할)뿐입니다.
> 목 계정에는 슈퍼 관리자가 없어서, 관리자 쪽 기대값은 백엔드 테스트 `label_studio/workspaces/tests/test_api.py`가 검증합니다.

## 4. 작업·검수 워크플로 테스트 (TC-WF)

자동화: `tests/api/02-annotation-review.spec.js`

상태 전이 요약:

```
작업자 제출 ──────────────→ 검수 대기 PENDING
검수자 승인 ──────────────→ 승인 ACCEPTED        (어노테이션 APPROVED)
검수자 반려 ──────────────→ 반려 REJECTED        (어노테이션 REWORK_REQUIRED, 작업 큐로 복귀)
   └ 작업자 수정 ─────────→ 다시 PENDING
검수자 수정 후 승인 ───────→ FIXED_AND_ACCEPTED  (무엇을 고쳤는지 자동 요약이 남음)
```

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| TC-WF-001 | 제출 → 검수 대기 | 작업자1이 A1의 다음 태스크에 라벨 제출 | 태스크 `PENDING`, 어노테이션 `COMPLETED`, 버전 1 |
| TC-WF-002 | 검수 대상 목록 | 작업자2 제출 후 검수자1이 검수 대상 조회 | 방금 제출한 태스크가 있고, 작업자 정보가 작업자2로 표시 |
| TC-WF-003 | 승인 | 검수자1이 승인 | 태스크 `ACCEPTED`, 어노테이션 `APPROVED`, 검수자 기록 남음 |
| TC-WF-004 | 반려 | 검수자1이 사유와 함께 반려 | 태스크 `REJECTED`, 어노테이션 `REWORK_REQUIRED`, 다시 작업 대상(`is_labeled=false`) |
| TC-WF-005 | 반려 후 재작업 | 반려된 작업을 작업자가 수정 | 태스크가 다시 `PENDING`, 어노테이션 `COMPLETED`, 이력에 반려 기록 유지 |
| TC-WF-006 | 수정 후 승인 | 검수자1이 결과를 직접 고쳐 승인 | `FIXED_AND_ACCEPTED`, 결과가 검수자 값으로 교체, 코멘트에 `부정 → 긍정` 요약 |
| TC-WF-007 | 잘못된 수정 후 승인 요청 | 수정 내용 없이 수정 후 승인 호출 | **400** |
| TC-WF-008 | 검수 없는 프로젝트 | B2(검수전략 NONE)에 작업자3이 제출 | 태스크 `NOT_SELECTED` — 검수 대상이 되지 않음 |
| TC-WF-009 | 진행률 집계 | 제출/승인 전후로 진행률 조회 | 제출 시 검수 대상 수 +1, 승인 시 검수 완료 수 +1, 전체 태스크 수는 시드 값과 일치 |
| TC-WF-010 | 이력 필터 | 검수 이력을 상태별로 조회 | 지정한 상태만 반환, 없는 상태값은 **400** |

### 5.2 작업·검수 수행

라벨링 화면은 별도 URL이 아니라 데이터 화면의 쿼리 파라미터입니다.
`/projects/<id>/data?labeling=1`(라벨 스트림), `/projects/<id>/data?task=<태스크id>`(특정 태스크).

| ID | 시나리오 | 절차 | 기대 결과 |
|---|---|---|---|
| TC-UI-201 | 라벨링 제출 | 작업자1이 라벨 스트림에서 `긍정` 선택 후 제출 | 저장 알림이 뜨고, 검수 대기 수가 +1 |
| TC-UI-202 | 작업자 화면 버튼 | 작업자1이 태스크를 열기 | 승인/거절 버튼이 **없음**(제출/건너뛰기만) |
| TC-UI-203 | 검수자 화면 버튼 | 검수자1이 같은 태스크를 열기 | `승인`·`거절` 버튼이 보이고 제출 버튼은 없음 |
| TC-UI-204 | 승인 | 검수자1이 승인 클릭 | 태스크가 `ACCEPTED`로 바뀜 |
| TC-UI-205 | 거절 | 검수자1이 거절 클릭 → 사유 입력 | 사유 입력창이 뜨고, 태스크가 `REJECTED`, 입력한 사유가 이력에 남음 |
| TC-UI-206 | 검수 내역 화면 | 검수자1이 `/projects/<id>/review` | `작업 내역` 화면과 해당 태스크가 보임 |
| TC-UI-207 | 검수 화면 차단 | 작업자3이 A1의 검수 화면 URL로 이동 | 검수 내역이 보이지 않음(역할 가드가 되돌림) |

> **거절 사유는 브라우저 기본 `prompt` 창**으로 받습니다. 자동화에서 대화상자 핸들러를 달지 않으면 자동 취소되어 거절이 조용히 무시됩니다 — 직접 스크립트를 추가할 때 주의하세요.

## 6. 수동 점검용 체크리스트

자동화되지 않았지만 화면으로 한 번씩 확인해 두면 좋은 항목입니다.

- [ ] 프로젝트 생성 마법사의 **작업자 할당** 단계에서 드래그로 배정한 결과가 저장되는가 (`/projects` → `생성`)
- [ ] 워크스페이스 **보상** 탭의 금액이 작업·검수 실적과 맞는가
- [ ] 데이터 화면의 `검수` 열 링크가 해당 태스크의 검수 이력으로 이동하는가
- [ ] 초대 링크로 가입한 사람이 지정한 역할로 자동 배치되는가 (`?tab=users` → `초대 링크 생성`)
- [ ] 워크스페이스/프로젝트 삭제 후 목록과 태스크 수가 정리되는가
